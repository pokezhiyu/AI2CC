# 设计空间文档交互规范

## 目的

设计空间承担可观察、可操作、可交接的设计表达。凡用于说明页面交互、用户流程、状态变化、原型行为或信息结构的设计成果，必须在对应的设计空间 Markdown 文档阅读页中直接呈现动态效果。

## 强制规则

1. **文档内呈现**：动态展示必须嵌入 `设计空间/` 下的目标 Markdown 文档，并随该文档在 Workspace 阅读模式中渲染。不得用独立展示页面、外部链接或聊天中的临时预览代替文档内成果。
2. **动态而非静态**：只要内容包含可选择节点、步骤推进、状态转换或信息分支，就必须提供可操作反馈。静态截图、普通 Mermaid 图或文字说明可以作为补充，但不能代替动态展示。
3. **Markdown 是事实来源**：交互内容及其文案、节点、顺序和状态定义保存在 Markdown 中。渲染器只负责解释与展示，不在页面组件中复制项目专属内容。
4. **就地反馈**：点击后必须在当前文档内立即更新选中状态、进度、详情或结果；不得要求跳转到另一个页面才能理解交互结果。
5. **保持可编辑**：阅读模式展示互动结果；编辑模式必须能查看并修改对应的结构化配置。配置无法解析时，阅读模式应显示可理解的错误提示。

## 支持的文档交互

### 顺序流程

使用 `interaction-flow` 围栏代码块表达步骤流程。至少提供：

- 可点击的步骤节点；
- “上一步”和“下一步”；
- 当前、已完成、未开始三类可辨识状态；
- 当前阶段的说明、产出与完成条件；
- 适合演示时提供“自动演示”，并允许暂停、重新演示或回到起点。

### 分支结构

使用 `interaction-mindmap` 围栏代码块表达思维导图或结构分支。至少提供：

- 可点击的一级分支；
- 明确的当前分支状态；
- 与当前分支联动的详情区域；
- 键盘左右方向键切换。

如果现有类型无法准确表达目标交互，应扩展通用文档渲染能力，再在设计文档中使用；不得为单篇文档制作一次性独立页面。

## 体验与无障碍

- 所有点击目标必须支持键盘操作，并具有可见焦点。
- 选中、播放和步骤状态必须通过语义属性暴露；动态变化应提供非打断式状态播报。
- 不得只依赖颜色表达状态，颜色必须配合文字、编号、形状或控件状态。
- 动效用于解释状态变化，不得自动无限播放；必须遵守系统的“减少动态效果”设置。
- 窄屏下允许流程横向滚动，但控件、详情和正文不得被遮挡。
- 视觉语言应继承当前项目设计规范，避免通用模板化外观。

## 工作方式

1. 按 Workspace Harness 加载相关设计知识与当前有效需求。
2. 从 Skill Registry 选择已启用且健康的 UI/UX 或前端设计能力，并在使用前读取对应 `SKILL.md`。
3. 先把交互内容写入目标设计空间文档，再补充或复用通用渲染能力。
4. 在真实 Workspace 文档路由中验证，不以独立 HTML 或组件演示页作为验收依据。
5. 将文档、通用渲染能力和必要样式一同提交到 Git，使后继 Agent 仅凭 Repository 即可继续维护。

## 完成检查

- 从左侧知识树打开目标设计文档即可看到互动内容。
- 点击节点后，选中状态和详情内容同步变化。
- 顺序流程可以前进、后退；启用自动演示时可以暂停，并会在终点停止。
- 键盘可以完成与鼠标等价的核心操作。
- 亮色、暗色和窄屏下仍能阅读与操作。
- Markdown 编辑模式保留完整配置，刷新后仍可由 Repository 重新生成。
