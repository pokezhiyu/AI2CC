# ADR-001：使用 Canvas 与原生 Web 技术实现贪吃蛇

## 状态

已接受。

## 背景

V1 需要在当前 Workspace 中快速开发和验证，并在后续独立正式环境中以静态站点部署。核心画面是固定网格上的高频位置更新，不需要复杂组件树、远程数据或服务端渲染。

## 决策

- 使用 HTML Canvas 绘制棋盘、蛇身和果实。
- 使用原生 ES Modules 组织游戏核心和界面控制。
- 使用 CSS 实现页面布局、响应式和控件状态。
- 将纯游戏规则放入 `game-core.js`，与 DOM 和 Canvas 分离。
- 使用浏览器 `localStorage` 保存按模式区分的最高分。
- V1 不增加业务后端和新的运行依赖。

## 原因

- Canvas 适合固定棋盘和每步整体重绘，模型直接、开销可控。
- 原生模块无需引入另一套构建体系，可由现有开发服务直接托管。
- 规则层与界面层分离后，可以对移动、碰撞、得分和穿墙规则做确定性测试。
- 静态产物易于迁移到独立生产环境，符合当前部署边界。
- 无远程服务可降低 V1 的隐私、安全和运维复杂度。

## 备选方案

### DOM 网格

优点是每个格子天然具备 DOM 语义；缺点是移动时需要频繁更新大量节点，渲染与样式状态更分散。V1 不采用。

### 集成到 Workspace Vue 组件

优点是复用现有 Vue 工程；缺点是把业务游戏与知识空间产品强耦合，不利于后续独立部署。V1 将游戏保存在独立 `snake-game/` 目录。

### 使用游戏引擎

可提供场景、资源和物理系统，但当前玩法规模不足以抵消依赖、包体和学习成本。V1 不采用。

## 后果

### 正面

- 可作为静态资源直接运行和部署。
- 核心规则容易测试和复用。
- 不依赖账号、网络和服务器。
- 源码结构小，Agent 可通过技术空间快速加载上下文。

### 代价

- Canvas 内的游戏对象没有独立 DOM 语义，需要用外部文字和控件补足无障碍体验。
- 复杂地图、动画资源或多人功能出现后，当前实现可能需要扩展或重新评估。
- Markdown 源码快照必须由生成脚本维护，不能手工形成第二份实现。

## 复审条件

出现复杂场景系统、多人实时对战、服务端权威状态或大量动画资源时，重新评估渲染技术和后端边界，并创建新的 ADR 替代本决策。
